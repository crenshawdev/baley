# Host matrix

The matrix measures whether Claude Code keeps agents from reading or writing Baley's home and its config folder, through shell commands and their children and through its built-in file tools. It also measures whether Baley's own hook and server still write the home, and whether the host hands the hook and the server what the design assumes. These are the probes behind acceptance gate 2 of [design 0001](../../docs/design/0001-evidence-ledger.md). It is a spike. Nothing here ships. Claude Code's probe is run before each release under ADR 0033 (`../../docs/adr/0033-host-security-bar.md`). The Codex probes stay as the instruments that measure Codex against the bar, should it return.

The live qualification measures the built `baley` binary against live Claude Code instead of stand-ins. It runs the artifacts `baley artifact` renders (the MCP registration, the hook and the settings) in a disposable tree whose home and config folders come from exported `XDG_DATA_HOME` and `XDG_CONFIG_HOME`. It drives two interactive sessions at once with subagents, `/cd`, `/clear`, `/branch`, exits and restarts, then reads the disposable ledger back. The stand-in probe stays the instrument that captures each tool's hook input and its field names. The procedure is [live-claude.md](live-claude.md). Each run's filled observation sheet is committed here with its date and run number in the file name, and this README holds a dated section per run. Every run below was driven by a coding agent through tmux: it started each interactive session, typed each step, approved each permission prompt and read every outcome from files and the ledger, except that the owner typed the login into the isolated configuration. No step used a non-interactive session.

The installed qualification measures what the development install leaves behind, again against live Claude Code. It installs unsigned development artifacts with `install.sh` into a disposable `HOME` and an isolated `CLAUDE_CONFIG_DIR`, so the owner's real stable path and Claude folder are never touched, and then drives interactive sessions over the wiring `baley install` wrote: what a new session loads, protection of Baley's home, its config folder, the versions folder and the stable path, an install rerun from a newer version, the opt-in and manual update paths, a newer hook beside an older server, and Claude Code's process ending while a call is in flight. The artifacts are built at the qualified commit and at the T14 merge, with the local edits `artifacts.txt` records, and are served from a throwaway branch of this repository for the run only. No release is published. They carry no signature, so a checksum over them shows that a download matched its manifest and nothing more. Signing and publication belong to the release design, issue 14. The procedure is [live-install.md](live-install.md), and its sheets are committed here as `install-live-<date>-run<n>.md`, filled the same way as the live qualification's.

The Claude Code probe uses two disposable stand-in folders, one for home (`~/.local/share/baley-matrix/claude/home`) and one for config (`~/.config/baley-matrix/claude/config`), so it never touches a real ledger or real settings. Its session is interactive and run by the owner. A hook and a stand-in MCP server record where they ran and write a marker into the home stand-in, and the owner asks the agent to read and write both stand-ins with each tool. The Codex probes keep their single stand-in, `~/.local/share/baley-matrix`, and each runs one throwaway non-interactive session from a subdirectory of this repository.

## Run it

Codex, all three probes:

```
sh probe-codex.sh
sh answer-test.sh
```

Claude Code (its sandbox needs `bubblewrap` and `socat` on Linux):

```
sh probe-claude.sh
```

The script clears and recreates its own folders under `baley-matrix/claude`, refusing when one is not owned by the user or a folder from HOME down to it is a symbolic link, then seeds both stand-ins with harmless fixtures and renders the settings: the sandbox on and required, write access over the two trees that hold the stand-ins (so a refused write comes from the stand-in's deny entry and not the default boundary), sandbox and permission deny rules over both stand-ins, and a hook matching Bash, Monitor, PowerShell, Read, Grep, Glob, Write, Edit and NotebookEdit. It then prints the procedure and writes an observation sheet, `observations.md`, into the results folder. It never starts `claude`.

The owner starts the printed interactive session from the printed folder, runs each step, approves any permission prompt so the result shows the deny rules and the sandbox, and fills in the sheet. The sheet also has the version, platform and date, and a field for each behaviour the Claude Code documentation leaves unclear. The PowerShell steps need `pwsh` 7 and are recorded as unavailable without it. No step starts a non-interactive session.

The live qualification of the built binary (it needs `bwrap`, `socat`, `sqlite3` and `jq`, and `pwsh` 7 for the PowerShell rows):

```
sh live-claude.sh <absolute path of a built baley>
sh live-claude-reads.sh
sh live-claude-restore.sh
```

`live-claude.sh` builds the disposable tree under `~/.local/share/baley-live`, renders every artifact from the binary, writes the observation sheet and prints the launch command of every session. It never starts `claude`. The sessions then follow [live-claude.md](live-claude.md) part by part. `live-claude-reads.sh` runs after the sessions and before `live-claude.sh` is run again, since that clears the tree. It prints the ledger checks, the exit lines, the hook timing and the comparison of the real folders, and its output is saved as `results/reads.txt`. `live-claude-restore.sh` runs once after the reads are saved, because it changes the ledger. It anchors project one on its disposable remote, copies the ledger, restores the copy behind that anchor, and prints the anchored `verify`, `acknowledge-restore` twice, the anchored `verify` again, the local-only `verify` and `doctor`, each with its exit status. It judges nothing, and its output is saved as `results/restore.txt`. It refuses to run when `results/reads.txt` is missing or a server of the disposable tree is still running. It does not check that the results folder holds no symbolic link (issue #235). All three scripts refuse to run when `BALEY_HOME` is set, even empty, because it collapses home and config into one folder. The sheet's mark on every row is pass, fail or unavailable, or observed for a row that records without an expectation.

The installed qualification of the development install (it needs `bwrap` and `socat` for the protection rows, `sqlite3` and `jq` to read the ledger and the settings back, `curl`, and a public repository to publish the throwaway branch to):

```
sh live-install-artifacts.sh <commit> <absolute build folder>
sh live-install.sh
sh live-install-reads.sh > ~/.local/share/baley-install-live/results/reads.txt
```

`live-install-artifacts.sh` builds three release binaries in git worktrees under the build folder, so this checkout is left as it was: `older`, the T14 merge with its version lowered to 0.0.1, `base`, the commit to qualify at 0.0.2, and `newer`, the same commit at its own version with two local edits, a changed `bal-capture` stub and `bal-help` dropped from the manifest, so an install rerun has a stub to replace and a stub to retire. It lays them out under `~/.local/share/baley-install-artifacts` the way `install.sh` reads them and writes `artifacts.txt`: each artifact's version, SHA-256, source commit and local edits, and the manifests. Publishing the three trees to the throwaway branch is the owner's step. `live-install.sh` builds the disposable tree under `~/.local/share/baley-install-live` (a disposable `HOME`, an isolated Claude folder holding seeded owner settings, two git projects and a results folder), writes the observation sheet and prints the environment prefix and the launch of every session. It never starts `claude` or `baley`. It clears its tree every time it runs, so it is run once, before the login. The sessions then follow [live-install.md](live-install.md) part by part, with the owner typing the login. `live-install-reads.sh` runs after the sessions. It prints the verify and doctor reports with their exit statuses, the install and update events, the captures, the guard answers, the stable link, the versions folder with the time each download finished, the Claude folder's wiring and the comparison of the owner's real installation with the values taken before the run. Its own queries open the ledger read-only, but the verify and doctor runs it makes can first bring views behind this binary's up to the current set, which is why it runs after the sessions and not between them. `live-install.sh` and `live-install-reads.sh` refuse to run when `BALEY_HOME` is set, even empty. When the record is committed, the throwaway branch is deleted.

The Codex scripts print the agent's own report, the hook's stdin, the server's working directory and which files landed in the stand-in home. `answer-test.sh` checks which hook answers Codex honours.
