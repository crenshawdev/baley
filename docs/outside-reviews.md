# API keys and outside-review risks

The design requires that Baley never read, store or send your API keys. Keys live in your environment, where every program Claude Code starts can see them, agents and subagents included. Nothing scrubs a key a command prints. Your code goes to the chosen provider under its terms.

Release 1 outside reviews use provider APIs only. Baley builds the request and names the address, header and environment variable; the session sends it with your key and returns the raw response for Baley to parse and check. The same boundary applies to model-list refreshes. Provider command-line agents are outside this release.

The interview records your confirmation of an outside provider, and `baley models update` prints a fetch command only for a provider with a current confirmation. Without one it refuses with `provider-not-acknowledged`, naming `baley config interview`. The same check before a review, including for settings edited outside the interview, is still Build 4's (#25). `baley config interview` asks which providers to use (`openai`, `deepseek` or `none`) after the settings questions, shows the warning above for each one you pick and needs a typed `yes` to it. Any other answer declines the whole interview and writes nothing. It then shows a summary that names every file it will change. After the final `yes` it records the acknowledgement in the ledger with your `owner.name`, or your git `user.name` when that is unset (it refuses, before the summary, when neither is set), adds the providers' API hosts to Claude Code's settings file, writes `review.reviewers` in `config.toml`, and then writes the settings. If a step fails, it reports the failure and the writes already completed. Running the interview again against the same file is safe and redoes any write that did not happen. Without `--global` or `--project`, a rerun inside a project writes your settings answers to `baley.toml` once `config.toml` holds a role value, so pass `--global` to rerun against `config.toml`. There is one exception: when the reviewer list was written to `config.toml` and the ledger policy step after it failed, a rerun finds the list already equal and does not redo that step ([#255](https://github.com/crenshawdev/baley/issues/255)). It asks again when the warning changes. A fresh install enables no outside provider; a reinstall keeps acknowledged choices and the hosts the interview added. Install never acknowledges a warning for you.

Baley holds no key. The `keys.env` reader, `baley exec --key` and the HTTPS model lister are gone, and a `keys.env` left by an earlier build stays in the config folder, unread and still protected. To refresh a provider's model list, run `baley models update [provider...]`. It prints a shell command for you to run, one per provider, which needs `sh` and `curl`: it fetches the list with the key from your environment, hands the key to curl on stdin so it never shows in the process list, and pipes the result into `baley models import <provider>`. The import records the new list, or keeps the previous one when the fetch failed or came back cut short. With no provider named, `update` covers the providers in `review.reviewers` that hold a confirmation. `baley install` and `baley init` seed the catalog from the list shipped in the binary, with no network call. The parked review engine also reads environment keys and `providers.env` and makes provider calls; that code goes with the parked engine in Build 9. See [the credential decision](adr/0039-session-owned-provider-credentials.md) and [configuration build status](design/0003-configuration-and-routing.md#11-build-status).
